# Deploying Cursus

The whole shape of this follows from one fact: **the app keeps its state on the
filesystem.** The database is a SQLite file and the CVs are files beside it.

That means one machine with one disk that survives restarts. It rules out
Vercel, Netlify and anything serverless, and it rules out running two instances
— they would each get their own disk and serve a different database. Scaling
past one instance means moving off SQLite first.

Everything below assumes Render, which is what `render.yaml` describes.

---

## First deploy

### 1. Create the service

Render → **New → Blueprint** → pick the `matancutler/cvrsus` repository. It reads
`render.yaml` and proposes one web service with a 5 GB disk mounted at `/data`.

It will then ask for the values marked `sync: false`. You can leave every one of
them blank for now except `APP_URL` — the app boots without them, and the next
section says what each one turns on.

### 2. The one value to get right on day one

```
APP_URL = https://<whatever-render-called-it>.onrender.com
```

This is where the links in emails point. Set it to the Render address now and
change it when you move to the real domain (step 6). Everything else in
`render.yaml` is already correct and needs no thought.

`SESSION_SECRET` is generated by Render and then held. Never change it: it signs
session tokens and hashes sign-in codes, so a new value signs everyone out and
invalidates every code in flight.

### 3. Watch the first boot

The log should end with:

```
Cursus API listening on http://localhost:10000
0 candidate(s), 0 company account(s)
```

Zero of both is correct — this is a new database on a new disk.

If you see `OTP_ECHO is on`, stop and fix it. With it on, knowing somebody's
email address is enough to sign in as them.

### 4. Create your real account

Company registration is open, and a new company is created **pending**: it can
sign in and finish setting up but reaches no candidate profile until approved.

1. Go to `https://<your-render-url>/hr` and create the company account.
2. Approve it from Render's shell — `list` first, because you need the id:

```bash
node server/scripts/companies.mjs list
node server/scripts/companies.mjs approve <id>
```

### 5. Turn on the parts that need keys

Add these in Render → Environment. Each one is optional; the app runs without it
and does less.

| Variable | Without it |
|---|---|
| `RESEND_API_KEY` | Emails are printed to the log instead of sent. Sign-in codes never arrive. |
| `MAIL_FROM` | Sends from Resend's `onboarding@resend.dev`, which only delivers to you. Set it to `Cursus <no-reply@mail.cvrsvs.com>`. |
| `MAIL_REPLY_TO` | Replies to a no-reply address go nowhere. |
| `ANTHROPIC_API_KEY` | CV reading and match scoring fall back to keyword overlap. |
| `VOYAGE_API_KEY` | Shortlisting matches wording rather than meaning. |

The two AI keys are what make the product the product. Without them the app is a
keyword search with a nice interface.

### 6. Point the domain

Once you are happy clicking through the Render address:

1. Render → Settings → Custom Domain → add `cvrsvs.com`.
2. Add the DNS record it gives you.
3. Change `APP_URL` to `https://cvrsvs.com`.

Your Resend sending records live on `mail.cvrsvs.com` and are unaffected. TLS is
issued automatically.

## Deploying again

`git push` to `main`. Render builds and swaps.

The disk is not touched by a deploy, which is the entire point of it being a
disk.

---

## Backups

There are none unless you make them. One machine with one disk is one failure
away from nothing.

```bash
node scripts/backup.mjs /path/to/somewhere
```

It writes a timestamped directory holding the database and every upload, then
reads the copy back and tells you whether every file the database names is
actually in it. That check exists because the opposite has happened here: rows
pointing at files that were not there. A backup of the database without the
uploads is not a backup.

The database is copied with SQLite's online backup API rather than by reading
the file. The app runs in WAL mode, so at any instant the `.db` file is missing
whatever is still in `.db-wal` — `cp` produces a file that opens fine and is
quietly a few transactions behind.

**Get the copies off the machine.** A backup on the disk you are protecting
against is not a backup either.

---

## Things that will bite

**`CKING_DATA_DIR` and `CKING_UPLOAD_DIR` are the two that matter.** Without
them the app still boots, still works, and writes the database and every
uploaded CV to the container's temporary filesystem — thrown away on the next
deploy, with nothing in the logs to say so. `render.yaml` sets both; if you ever
create the service by hand, set them by hand.

**`server/.env.production` is not loaded by anything.** `import 'dotenv/config'`
reads exactly one file, `.env`, in the working directory. There is no
NODE_ENV-aware lookup. The file is kept as a note to self and marked as such at
the top.

**One instance only.** If Render ever offers to scale this service, the answer
is no until the database moves off the filesystem.

**Node is pinned to 22** in both `render.yaml` and `.node-version`.
`better-sqlite3` ships prebuilt binaries per Node major; an unpinned runtime is
how a build starts compiling from source one morning.

**Restarts run a sweep.** On boot the server moves any upload no database row
references into `uploads/_swept/`. It moves rather than deletes, deliberately —
the guard that decides what is referenced reads five columns across four tables,
and a moment when that function is wrong used to mean files nobody could get
back. Startup also prints every row whose file is missing.
