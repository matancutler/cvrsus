Running the site

The API is Express on port 5175; the Vite client serves on 5174 and proxies to it. npm run dev starts both together and is what you want almost always.

npm run dev Writes

Starts the API and the client together, both watching for changes.

Normal day-to-day. Leave it running while you work.

npm run dev:server · npm run dev:client Writes

Runs one half on its own.

One side is misbehaving and you want its output uncluttered.

npm run build Read

Compiles the client into client/dist.

After any front-end change you want the API to serve, and before running the test suite — several suites read the built bundle rather than the source.

npm run start Writes

Runs the API alone, no watcher, serving the built client.

Production, or checking a build behaves the way it will when deployed.

Reading the database

All read-only, and password hashes and sign-in codes come back redacted — there is no plaintext credential in here to leak.

npm run db Read

A row count for every table.

First thing when something looks wrong and you do not yet know where.

npm run db accounts Read

Companies and their recruiters in detail.

Checking who exists, who is an admin, which companies are still pending.

npm run db billing Read

Seat limits and seat purchases.

A company disputes what they were charged, or seats do not add up.

npm run db candidates | messages | views | folders Read

The same detail view for each of those areas.

Tracing one specific thing rather than surveying everything.

Companies & approval

A new company registers itself and lands as pending: it can sign in and finish setting up, but reaches no candidate profile until somebody approves it. Approving is how a recruiter account actually goes live.

The one you will use most. Approval sends the company its key by email and lets every recruiter on the account start searching. Until then they see the in-review screen.

node server/scripts/companies.mjs pending Read

Every company waiting for a decision.

Start here. This is your approval queue.

node server/scripts/companies.mjs approve <id|name> Writes

Activates the company. Its recruiters can now search and reveal.

You have checked the company is real and the person asking works there.

node server/scripts/companies.mjs decline <id|name> [--reason "…"] Writes

Refuses the account. Its recruiters can still sign in and see their own screens, but reach no candidate profile. The reason is stored for your records and is deliberately not sent to them.

You could not verify the company, or it is not a real employer. Reversible — approve undoes it, and the candidate is none the wiser either way.

node server/scripts/companies.mjs list Read

Every company, approved or not.

Finding an id, or checking a name is not already taken.

node server/scripts/companies.mjs show <id|name> Read

One company in full — key, recruiters, status, balances.

Answering a support question about a specific account.

node server/scripts/companies.mjs add "Acme Hiring" --admin "Maya Cohen" [--password "…"] Writes

Creates a company and its first admin, through the app's own functions — same key generation, same password hashing as the sign-up form.

Setting up an account on somebody's behalf, or seeding a demo.

node server/scripts/companies.mjs rename <id> "New Name" Writes

Changes the company name.

They rebranded, or the name was typed wrong at sign-up.

node server/scripts/companies.mjs delete <id> Read

Dry run. Shows everything that would be removed and deletes nothing.

Always, before the real thing.

node server/scripts/companies.mjs delete <id> --yes Destroys

Actually deletes, cascading through the nineteen tables that reference a company or its recruiters.

Never on company 1. Use this rather than SQL — none of those tables declare a foreign key, so a hand-written DELETE leaves orphans nothing will notice for months.

Recruiters

Individual seats inside a company. A recruiter cannot search until the company they belong to is approved.

Passwords can be set, never read. They are stored as salted scrypt hashes. There is no command that returns somebody's password, and adding one would mean storing them reversibly — so anyone with a copy of the database, or an old backup, would have all of them.

node server/scripts/recruiters.mjs list [company] Read

Every recruiter, or just one company's.

Finding a username or an id.

node server/scripts/recruiters.mjs show <id|username> Read

One recruiter in full.

Checking whether somebody is an admin, or still active.

node server/scripts/recruiters.mjs add <company> "First Last" [--password "…"] [--admin] Writes

Adds a seat. --admin makes them an organisation administrator.

A company asks you to add a colleague for them.

node server/scripts/recruiters.mjs set <id|username> [--first X] [--last Y] [--admin true|false] Writes

Corrects a name, or grants and revokes admin.

Somebody was promoted, or left and should lose admin first.

node server/scripts/recruiters.mjs password <id|username> [--password "…"] Writes

Sets a new password. Omit the flag and one is generated for you.

They are locked out and the self-service reset email is not reaching them.

node server/scripts/recruiters.mjs delete <id|username> [--yes] Destroys

Removes the seat. Their folders and saved work pass to a remaining colleague; the organisation keeps the candidates it paid to reveal.

Somebody has left. Never on recruiter 1 or 72.

Candidates

Job seekers. There is deliberately no add command — an account is created by uploading a CV, and the CV is the whole basis of the profile.

Edit here, not in SQL. These commands bump the profile version, which invalidates the cached match analyses built on the old values. Raw SQL does not, and leaves recruiters reading conclusions drawn from data that no longer exists.

node server/scripts/candidates.mjs list [--search text] [--limit 50] Read

Candidates, newest first, optionally filtered.

Looking for somebody when you only have part of a name.

node server/scripts/candidates.mjs show <id|email|phone> Read

One candidate in full — contact details, city, when they applied, freshness state, documents, and what a deletion would remove.

Any support question. A phone number works as the lookup, using its last nine digits, so formatting does not matter.

node server/scripts/candidates.mjs set <id|email> [--email …] [--phone …] [--first X] [--last Y] [--location …] [--summary "…"] Writes

Corrects any profile field. Refuses an email or phone another account already holds, and names the account that has it.

Account recovery, or fixing something they cannot fix themselves.

node server/scripts/candidates.mjs activate <id|email> Writes

Puts a hidden profile back into recruiter search and resets the activity clock.

They were auto-hidden after 60 days of silence, or deactivated themselves and want back in.

node server/scripts/candidates.mjs deactivate <id|email> Writes

Takes them out of search immediately. The account and its data stay.

They asked to stop being approached but do not want to delete anything.

node server/scripts/candidates.mjs delete <id|email> [--yes] Destroys

Erases the profile, the files, everything derived from them, the messages, and the notes recruiters wrote. Without --yes it shows you what would go.

A verified erasure request. Never on candidate 6912 — that is your own profile.

Deleting & editing accounts

The commands live with each kind of account above. What they actually destroy differs a great deal, so this is the same three commands compared side by side.

All three are a dry run without --yes. Run it once bare, read what it says it would remove, then run it again with the flag. There is no confirmation prompt to catch you — the missing flag is the prompt.

  Candidate Recruiter Company
Command candidates.mjs delete <id|email> --yes recruiters.mjs delete <id|username> --yes companies.mjs delete <id> --yes
Destroys The profile, the CV and every uploaded file, everything read out of them, the message history, and the notes, tags and shortlist entries recruiters wrote about them. Their messages and conversations, saved searches, search history, outreach drafts and any outstanding password-reset link. Everything belonging to the company and to every recruiter on it, across nineteen tables.
Survives A billing ledger line carrying only the internal account number, so the organisation's accounts still reconcile, and an anonymised note that a deletion happened. Their folders pass to a colleague — an org admin first, otherwise the longest-standing seat. The organisation keeps the candidates it paid to reveal; only the departed recruiter's name comes off them. Nothing but the billing ledger.
Watch for Never candidate 6912 — that is your own profile. Recruiters lose the reveal they paid for and get no refund. Never recruiter 1 or 72. If they were the last seat there is no heir, and their folders go too. Deleting also erases the candidate's side of every conversation they had. Never company 1.

Changing details instead

Most support requests are a correction, not a deletion. Prefer these — they are reversible and they keep the account's history.

node server/scripts/candidates.mjs set <id|email> --email … --phone … --location … Writes

Corrects a candidate's details. An email or phone another account already holds is refused, and the refusal names the account holding it.

A typo, a new address, a changed number. Also the recovery route when somebody has lost their mailbox.

node server/scripts/recruiters.mjs set <id|username> --first … --last … --admin true|false Writes

Corrects a recruiter's name, or grants and revokes admin.

Somebody was promoted, or is leaving and should lose admin before anything else happens.

node server/scripts/candidates.mjs deactivate <id|email> Writes

Takes a candidate out of search without destroying anything. activate puts them back.

They asked to stop being approached. Reach for this before delete — it is what most people actually want, and it is reversible.

Do not edit the database directly. Two things go wrong quietly.

A hand-written UPDATE skips the profile version bump, so recruiters keep reading cached match analyses drawn from values that no longer exist. A hand-written DELETE leaves orphans: almost none of these tables declare a foreign key, so the rows that referenced the deleted one simply point at an id that is gone, and nothing notices until something reads them months later.

Account recovery

A candidate who cannot reach the mailbox they signed up with has no way in on their own — sign-in is the email address. They contact you, and you move them.

Step 3 is the whole job. Move an account to whatever address asks for it and anyone who knows a candidate's email can take their profile — CV, phone number and recruiter conversations included. A completed move frees the old address, so the real person cannot get back in either.

  1. Read the message

    There is no admin screen; this CLI is the inbox.

    node server/scripts/contact.mjs list
node server/scripts/contact.mjs show <id>

  2. Find the account

    By their old address, or by the phone number on the profile.

    node server/scripts/candidates.mjs show 052-123-4567

  3. Prove it is them — ring the number on file

    It was verified by SMS at sign-up and only the real candidate answers it. If they cannot take a call, cross-check the city, the roles in their CV and roughly when they applied. Knowing the old email address proves nothing: that is the one thing an impostor is certain to have.

  4. Move the address

    node server/scripts/candidates.mjs set <id> --email new@address.com

    If it refuses, they already made a second profile — decide which row survives before going further.

  5. Tell them

    By hand, from your own mailbox; nothing automates this yet. They then sign in normally, with profile, CV, messages and reveal history intact.

Contact inbox

The contact form stores every message and prints one line to the server console. Nothing else reads them back, and a console line scrolls away — so a real enquiry can sit unread for months. Check this on a schedule.

npm run contact Read

The twenty most recent enquiries.

Daily, or whenever you sit down to support.

node server/scripts/contact.mjs list --limit 50 Read

More of them. Add --all to include the test suite's own noise.

Catching up after a gap.

node server/scripts/contact.mjs show <id> Read

One message in full.

The list truncates; this does not.

node server/scripts/contact.mjs purge-tests --yes Destroys

Deletes rows the test suite created, and only those.

The inbox is drowning in fixtures after a heavy test run.

Maintenance

The freshness sweep — reminders at 30, 37, 44, 51 and 58 days, hidden at 60 — runs by itself on every server boot and daily thereafter. Revalidation does not, on purpose.

node server/scripts/revalidate.mjs Read

Dry run. Shows which profiles would be rebuilt and does nothing.

Always first. This is the default for a reason.

node server/scripts/revalidate.mjs --run [--limit 100] Writes

Rebuilds stale profile analyses.

Deliberately manual: rebuilding spends money on candidates' behalf, so it should be a decision somebody makes rather than a default they inherit. Use --limit to cap the spend.

Keeping and deleting CVs

Nothing in this product has ever deleted an applicant's CV. That was defensible while a Triage was a one-off report finished in an afternoon; it is not defensible for a session designed to stay open for weeks, because it means holding other people's CVs forever.

The sweep does not delete anything yet, on purpose. It runs daily, works out exactly what the rule would remove, writes that in the log, and stops. Read those logs for a full cycle before letting it act. There is no undo and no backup to restore from.

Turning it on is TRIAGE_RETENTION_DELETES=1 in Render and a restart.

The rule

A CV goes 90 days after its session is closed, or 12 months after it was uploaded, whichever comes first. Both are settings — TRIAGE_RETAIN_AFTER_CLOSE_DAYS and TRIAGE_RETAIN_MAX_DAYS — and either can be set to 0 to switch that half off. The second one is the one that actually binds: without it, a session left open keeps everything indefinitely.

The date is written on the session when it closes, so changing the setting later cannot move the date on sessions already closed under the old rule, in either direction. What goes is the CV, its file, its extracted text and its analysis. What stays is the session, its counters and its billing line — the accounts still have to reconcile.

npm run score:migrate Read

Dry run. Shows how many stored analyses the current scoring version would rescore, how far their numbers move, and how many verdicts cite a quote that is not in the CV. Writes nothing. Says “Nothing to do” if the migration has already run, which is the ordinary answer — the server runs it itself on the first boot after a scoring-version bump, so by the time you type this it is usually done.

After changing the scoring arithmetic, before letting it near anything.

npm run score:migrate -- --run Writes

Rescores every stored analysis from the verdicts already on disk — no model calls. Search gets new rows beside the old ones and overwrites nothing, ever; Triage is updated in place, with the previous contents of each row recorded so the revert can put them back exactly.

Rarely, because the server already does it: index.js runs this before it accepts the first request, and skips it on every boot after. Type it yourself only if the boot log said the migration failed, or after a revert. Add --force to run it again once it has run, and --job 42 or --triage 7 to do one first and look at the result.

npm run score:migrate -- --revert --run Writes

Undoes exactly one run and nothing else. Every row the migration wrote is recorded — the key of each Search row it actually inserted, the previous contents of each Triage applicant it overwrote — so this removes those and restores those, and leaves alone every analysis written by ordinary use since. There are no backup tables: the record is row-exact, and a full copy of both tables would have sat outside account deletion and outside the Triage retention sweep, holding the text of CVs that had been erased everywhere else.

Set SCORE_MIGRATE_ON_BOOT=off as well if you want the revert to stick. Otherwise the next restart migrates again, because as far as the server is concerned there is nothing recorded as done.

If the new scores are wrong. Then set MATCH_V_SCORING=2 and restart — the old rows were never touched, so they are found again immediately.

npm run score:migrate -- --refresh --run Writes

Re-applies the CURRENT MATCH_SILENCE_FRACTION to every analysis already on the live scoring version. No model calls: it rescores the verdicts that are already on disk and adds each row's stored location nudge back on top. Recorded like any other run, so -- --revert --run puts it back.

After changing the silence fraction. Without it the new value reaches only analyses written from then on, so every folder and every saved search keeps its old numbers and the dial looks broken.

npm run triage:retention Read

Every CV past its date, which session it belongs to, and which clock says so.

Any time. This is the list to read before trusting the sweep.

node server/scripts/triage-retention.mjs --triage <id> --run Destroys

Deletes the CVs past their date in that one session.

On test data first. --run over every session is refused unless you also pass --all, because a missing flag should not be the difference between seven made-up CVs and the whole disk.

npm run sweep:quarantine Read

What is sitting in uploads/_swept, how much space it takes and how old it is.

When the disk is filling. The boot sweep never deletes an orphaned upload — it renames it in there — and nothing has ever emptied the folder.

node server/scripts/sweep-quarantine.mjs --older 90 --run Destroys

Deletes quarantined files older than that many days.

After reading the list. --run needs --older: a file quarantined ten minutes ago is the one most likely to have been quarantined by mistake, and a file the sweep misjudged is a real CV.

Removing one CV

A single CV can be deleted from a running session — the author of the session or an organisation administrator, through DELETE /api/hr/triage/<id>/applicants/<applicantId>. There is no button for it yet; it exists because the Terms promise to assist with erasure requests and until now the only available action was deleting the whole session. Nothing is refunded: the CV was read, which is the work that was paid for.

There is no close button. The retention clock's ninety-day period runs from when a session is closed, and nothing closes one yet — so in practice only the twelve-month clock binds today, measured from each CV's upload. A session that finished long ago is treated as closed on the day it completed.

The AI layer

Every model call falls back to keyword matching when it fails, on purpose — a recruiter who loses a shortlist to one timeout is worse off than one who gets a cruder ranking. The cost of that design is that the product can lose its reasoning entirely and still look like it is working, which is what the first two commands here exist to catch.

If spend is running away, set AI_PAUSED=1 in Render and save. Every model call switches off, scores come from keyword matching, and nothing breaks. It takes effect on the next restart and needs no deploy. Unset it to bring the model back.

What each setting does

Setting Default What it changes
AI_PAUSED off Turns every model call off. The emergency brake.
MATCH_EFFORT high How hard the model thinks about each CV. Thinking is billed as output, so this is the single largest lever on cost — medium is roughly a third of the price. Do not change it without running npm run ai:eval first.
MATCH_MODEL claude-opus-5 Which model judges candidates. Part of the analysis cache key, so switching it does not serve old answers under a new name — but it does mean every reopened search re-analyses once.
WRITER_MODEL claude-sonnet-5 Writes the paragraph and interview questions when a recruiter opens a candidate. A writing job, not a judgement, which is why it is the cheaper model.
MATCH_SILENCE_FRACTION 0.35 What an unanswered requirement earns, as a share of its weight. A CV that does not mention Kubernetes is not a CV saying the candidate cannot do it, so silence costs something rather than everything. Raise it and thin CVs climb; lower it and only what a CV actually evidences counts. It applies to analyses written after the change, not to ones already stored — to move those, run npm run score:migrate -- --refresh --run, which rescores every stored analysis at the new value without a single model call.
MATCH_COVERAGE_FLOOR 50 Below this much of the job checked, a candidate card shows an amber Needs review chip; above it the card shows nothing and the percentage is in the dialog. Purely a label: it changes no score and no ranking. Like the silence fraction it is frozen into each row when the row is written, so changing it relabels nothing already stored until you run npm run score:migrate -- --refresh --run.
SCORE_MIGRATE_ON_BOOT on Set to off to stop the server rescoring stored analyses at startup. Only worth doing if a migration is misbehaving and you want the site up while you look at it.
MATCH_DAILY_CAP 1500 Model-read analyses per company per rolling 24 hours. A circuit breaker, not a budget: over it, scoring falls back to keyword matching.
DEMO_DAILY_CAP 200 The same, globally, for the public demo — the one surface with no account behind it and no limit on how many browsers exist.
PUBLIC_DEMO_DEEP 8 How many candidates the demo reads deeply to show its six cards. It used to read twenty-five.
PUBLIC_DEMO_MODEL claude-sonnet-5 The demo judges on the cheaper model. Strangers are not paying customers.

Two settings for rolling Triage

Setting Default What it changes
TRIAGE_ADD_CVS on Whether the Add more CVs button appears on a running Triage. Set it to 0 to take the button away; the route goes with it. One variable and a restart, no deploy, and nothing about the stored data changes either way.
TRIAGE_LOW_WATER 50 How many CVs of capacity count as running low. Crossing it downwards emails the organisation's administrator, once, and buying more arms the warning again. Set it to 0 to switch the warning off. The old behaviour — one email at exactly zero — could be stepped straight past, because a delivery bigger than the balance is refused rather than partially spent.

What changed for Triage

A Triage score is now that candidate against the role, on its own. It used to be scaled against the best CV in the pile, which meant a strong arrival quietly lowered everybody else's number. Scores no longer move; positions still do, when a stronger CV lands above someone. Opening an old Triage may therefore show different numbers than it did before — lower is not worse.

CVs now arrive in deliveries. A session can take a second or third pile while it is already running: each delivery is parsed and ranked on its own, and ranks already given out never move. The queue also looks for work every few seconds (TRIAGE_WAKE_MS), so analysis finishes whether or not a browser is open.

Add more CVs is a button on a Triage that is already running. Pick the files; they are read, ranked against the same job description and slotted into the list in their place by score. A score already on screen never moves.

Each delivery is charged on its own. A session used to be charged once, at launch. Now the charge belongs to the delivery — one ledger line per pile, naming the session and the delivery it paid for — and a file that turns out to be unreadable is refunded against its own delivery rather than against a total that might have been spent months earlier. A recruiter who is short of capacity is refused before anything is written, and the CVs come back rather than sitting half-added.

A candidate who applies twice is one person. The email decides: same mailbox, newest CV wins, and the older one stops appearing in the results. Both were charged, because both were read. A CV with no readable email is always a new person.

An analysis that failed can be retried for nothing. Those CVs were paid for when their delivery arrived, so the retry finishes work that was already bought.

A recruiter still sees the first fifty analysed immediately and twenty-five more each time they reach the end of a page. Nothing analyses a pile of three hundred CVs in full unless the recruiter reads that far.

After a deploy that touches the AI

  1. Run one search or Triage on the live site

    Anything that makes the product judge a CV.

  2. npm run ai:health

    In Render → the cursus service → Shell. It should say analyses used a model. If it says everything fell back, the model layer is failing silently and the scores on screen are keyword matches.

  3. npm run ai:cost --days 1

    Dollars per CV, and how much of the reading came from the prompt cache. A cache share near zero on a batch of twenty-five means caching is not working, which costs about double.

Tests

The API has to be running first, and the client built — several suites read the built bundle. Point them at a spare port rather than your working server: CKING_URL=http://localhost:5199.

Node 24 crashes on exit even after a clean pass, so the verdict is the “All checks passed.” line, not the exit code.

npm run test:<name> Writes

Runs one suite. They create their own fixtures and delete them again on the way out.

After changing anything the suite covers. Pick the closest one by name.

npm run ai:health Read

Is the AI layer actually running? Shows how many analyses used a model rather than the keyword fallback, and why the rest fell back. Names a spend limit as a spend limit rather than leaving it looking like a bad request.

When scores look cruder than they should, and after any deploy that touches the model settings. Every AI call falls back silently by design, so this is the only place the failures are visible.

npm run ai:cost [--days 7] [--by stage|model|day] Read

What the model calls actually cost, from the ledger: dollars per CV by surface, how much of the reading came from the prompt cache, and what the public demo has spent.

On the live service — this laptop has no key and has therefore never spent anything. Before and after any change meant to make the AI cheaper.

npm run triage:audit Read

What is in the live database before a Triage migration: sessions by state, CVs and their age, disk used, how many CVs were charged for and never analysed. Opens the database read-only, so it cannot write even by accident.

Before any Triage migration, and whenever the retention rule needs checking against reality. Run it on the service, not a laptop.

npm run data:test Writes

Creates a test recruiter with capacity, a job description and a handful of sample applicants, and leaves three more CVs in sample-cvs/ to add by hand. Made-up people, so nothing real is at stake.

On a local server you want to click around in. Never against production — it registers a company and spends capacity.

npm run ai:prefix Read

How many tokens the cached part of a match request is, asked of the provider rather than estimated, and what that is worth over a batch of 8, 25 and 50.

In Render → Shell, after changing the instructions or the shape of the request. The prefix's share of the request is the saving; if it falls, caching is worth less than it was. Costs nothing — counting tokens does not run the model.

npm run ai:eval --configs baseline,opus-medium --dry Spends

Judges the same CVs under several models and effort levels and reports how far each agrees with what production runs today. Writes the must-have disagreements without saying which setup produced which reading — read those before the key.

Before switching the judging model or its effort. Roughly $25-30 a run, so it refuses to start without --yes; --dry prints the plan and spends nothing.

npm run ai:eval -- --extraction --yes Spends

A different question from the one above. That measures judgement — does a cheaper model rank people the same way. This measures reading: does a cheaper model pull the same title, skills and dates off a CV. It reports agreement per field, because the fields fail differently — a wrong title shows on every card, a missed skill is invisible and costs retrieval, a wrong date moves seniority and therefore the ranking.

Before considering a cheaper extraction model. Extraction runs on Opus today at roughly 2.4 cents per CV, on a read-and-report task already at the lowest effort, so it is the cheapest saving available if the agreement holds. Reports only — it changes no default. Pennies per run at five CVs.

npm run prose:scan Read

Finds model-written text already in storage that is not language: a reason that is empty, one token repeated, far over its length cap, or without a letter in it. A verdict was once stored with its reason set to the word “ok” repeated twenty-one times — it satisfied the schema, parsed as JSON, and would have been shown to a recruiter as this product’s explanation of a judgement. -- --show prints the offending text.

After any run of analyses you want to trust. The check now runs before anything is written, so this is for rows written before it existed.

npm run prose:scan -- --repair Writes

Replaces corrupt reasons and explanations with a placeholder that reads as a placeholder. The verdict, the quote and the score are untouched — only the prose — and strengths and gaps are recomputed, since they are derived from reason.

After reading the scan. Re-analysing the row instead would be the thorough answer and costs a model call per candidate per job; this makes the row honest for nothing.

npm run score:rubric Read

Counts the analyses a rubric version bump could not carry forward, and what asking the model to redo them would cost. A rubric bump changes what the model is told a verdict means, so the verdicts themselves move — no arithmetic over the old ones produces the new ones. score:migrate carries forward every keyword-scored row, because those never saw the prompt, and leaves the model-written ones alone.

After a deploy that raised MATCH_V_SCORING for a rubric change. Reading it is free and tells you the size of the decision.

npm run score:rubric -- --run Spends

Re-asks the model for every deferred analysis, through the same function a live search calls — same prompt, same quote check, same cache key — so the rows it writes are indistinguishable from the ones a search would have written. Records each one in the migration manifest, so npm run score:migrate -- --revert --run undoes it. -- --limit 25 does a first tranche; -- --job 12 does one job.

Only if you would rather not wait. Doing nothing is also correct: a row left at the old version is a cache miss at the new one, so the next search of that job asks the model anyway and writes the answer. This only brings the bill forward. Re-running after a crash costs nothing for the work already done.

npm run unpoison Read

Finds cached analyses that are keyword guesses filed under a model’s name. Until September 2026 a candidate the model never answered for — aborted, timed out, rate-limited, or reached while the Anthropic balance was spent — had their fallback score written into the cache under the real model’s name, and served back on every later search as the product’s judgement. Nothing expires it. -- --show prints a line per row; -- --since 2026-09-01 narrows the window.

Once, after the September 2026 deploy, on any database that ran while the balance was exhausted. A count of zero is the expected answer on a box that always had credit.

npm run unpoison -- --delete --all Deletes

Removes them, so the next search of each job asks the model about those candidates again. --delete without --all or a --job is refused. Only rows carrying all three marks are deleted — the model/source disagreement, no verdicts in the blob, and no explanation; anything carrying one but not the others is printed and kept.

After reading the plan. It names how many are the last analysis for a candidate filed in a folder, because those cards lose their score and their reasoning until somebody runs that search again. There is no undo.

npm run seed:candidates -- --run Spends

Turns the CVs in eval-material/cvs/*.txt into real candidate profiles, through the steps an upload runs: extraction, then the taxonomy intelligence retrieval reads, then the embedding. A hand-written row would have no concepts and no vector, so it would be invisible to two thirds of the retrieval blend. -- --remove --run takes back exactly what it created.

Before testing anything about retrieval or ranking on a laptop. Local only — those CVs carry real names and phone numbers, so it refuses outright if CKING_DATA_DIR points at the production disk. A few pence per CV.

npm run recall:test -- --band 200 --yes Spends

Measures what the deep-analysis cap costs you. Takes each job's real retrieval ranking over the real pool, deeply analyses the top band of it, sorts by the fit each candidate actually earned, and then counts how many of the final top 20 were ranked below each candidate depth. Those are the people that depth would have lost. Reads the job descriptions from eval-material/jobs/*.txt.

Before changing MATCH_POOL_SIZE or the analysis cap. It can show a depth is too shallow and can never show one is deep enough — anybody ranked below the band is invisible to the test as well. Needs a pool several times larger than the top list to mean anything, so it is a production command.

npm run infer:backfill Read

Dry run. Counts the profiles extracted before inferred capabilities existed, and prices the backfill from the actual length of those CVs rather than an assumption.

Always first. This is the default.

npm run infer:backfill -- --run [--limit 50] Spends

Asks the cheap model what each CV's work implies but never states, and stores it beside the stated skills — never merged with them, at a lower confidence, under its own label type. Retrieval matches both; judgement is told an inference is a hypothesis and can never carry a requirement on its own.

Once, after inferred capabilities shipped. --limit does a tranche first so you can read what it produced before paying for the rest. It merges one key into each stored profile rather than re-extracting, so a candidate's own corrections survive.

Git, GitHub & deploying

Render deploys the main branch and nothing else. Pushing to any other branch saves your work to GitHub and changes the live site not at all — which is the point of working on a branch. A push to main starts a deploy within about a minute, and the site answers 502 for a minute or two while the old instance stops and the new one starts. That gap is normal.

git push -u origin main pushes the branch called main. If you are standing on another branch it sends nothing new, and nothing deploys. Check where you are with git branch --show-current.

git push origin <branch>:main Deploys

Puts a branch's work on the live site.

When the branch is finished and tested. Watch Render → Events for the deploy, and check /api/health comes back at 200 afterwards.

git push origin <last-good-commit>:main --force-with-lease Deploys

Rolls the live site back to an earlier commit.

When a deploy broke something and you want the previous version back now. Render's dashboard can also roll back to a previous deploy, which is the same thing with buttons.

A deploy can change the live database. New columns and tables are created on boot. They are only ever added, never dropped, so the previous version still runs against the newer database — which is what makes a rollback safe.

Committing is a local save point; pushing copies it to GitHub. Commit whenever you finish something coherent, push at the end of a session.
