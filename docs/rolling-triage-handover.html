Rolling Triage Handover

Five phases, built on the rolling-triage branch and not merged. What it does now, what it costs to test, the decisions I took on your behalf, and the four that are still yours.

What actually changed

A Triage was a report: one pile of CVs, ranked once, charged once, finished. It is now a place to work — and every part of that had to be built, because almost nothing in the old pipeline could run twice.

  • A session stays open. Add more CVs while it is running; they are read, ranked and slotted into the list in their place. A score already given never moves.
  • Each delivery is charged on its own. One ledger line per pile, naming the session and the delivery. An unreadable file is refunded against its own delivery.
  • Sessions have a life. Open, paused, closed — and closed starts a retention clock.
  • One CV can be deleted. Which is the first time an erasure request has had an honest answer.
  • The queue finds its own work. Analysis finishes whether or not a browser is open.
  • A candidate who applies twice is one person, matched by email, newest CV winning.
  • Scores are absolute. Each candidate against the role, on their own — not rescaled against the best CV in the pile, which is what used to make an arrival quietly lower everybody else's number.

Nothing is live. main is unchanged since the bug-fix release. Twenty-one commits sit on rolling-triage: 54 files, about 10,600 lines added.

Four decisions still yours

Each of these touches what customers are charged, what data is destroyed, or the legal wording — so I built the machinery and stopped.

Turn on “Add CVs” in production

Yours

TRIAGE_ADD_CVS=1 in Render, and a restart. It is on everywhere else. Off in production until you have run the cost test and picked an effort setting, because a second delivery is a second charge and the button should not be in front of paying recruiters before we know what each press costs us.

Pick the daily analysis cap

Yours

MATCH_DAILY_CAP is 1500 per company per 24 hours — about ten times any plan we would sell, so it does not bind. Under rolling sessions it should.

I did not lower it. Over the line, scoring silently falls back to keyword matching, so a cap set too low gives paying recruiters plainer readings than the ones they bought. npm run triage:audit now reports the busiest real company-day. Pick from that number, not from a guess.

Let the retention sweep delete

Yours

TRIAGE_RETENTION_DELETES=1. Today it runs daily, works out exactly what the rule would remove, writes that in the log, and stops.

Read those logs for a full cycle first. There is no undo and no backup — deleting other people's CVs on a schedule is the least reversible thing this product does.

Publish the Terms and privacy wording

Yours

Two live clauses stopped being true. Privacy 7A says CVs are kept “for as long as the Organization keeps the workspace” — honest about an afternoon's report, and “forever” about a session designed to stay open. And we promise to assist with erasure requests while having no way to remove one person's CV.

Replacement text is drafted and visible on the dev server at /terms and /privacy, in a red dashed box. It is absent from the production bundle — not merely hidden, absent; a test asserts that against the built file. Three questions for whoever reviews it are listed at the end of the draft.

Decisions I made for you

Judgement calls I took rather than stopping for. Each is a setting or a small change if you disagree.

Both versions of a duplicate person stay charged

Mine

When somebody applies twice, the older CV is set aside — but it was read, which is the work that was paid for. No refund. It is counted separately in npm run triage:audit so the gap between what was bought and what is shown is visible.

Deleting a CV refunds nothing

Mine

Same reasoning, plus one more: attaching a refund to a privacy right would make erasure a way to reclaim capacity, which invites exactly the wrong behaviour.

Low balance warns at 50 CVs, once per descent

Mine

TRIAGE_LOW_WATER. The old email fired at exactly zero, which a rolling session steps straight past: a delivery bigger than the balance is refused, so the balance sits where it is and nobody is told. Buying more arms the warning again.

25 open sessions per organisation

Mine

TRIAGE_MAX_OPEN_SESSIONS. An open session with nothing running is free storage on our disk and nothing else capped it. A number nobody working legitimately will meet; not a plan limit, and it should not be sold as one.

Old sessions read as closed without a migration

Mine

Q10 asked for existing Triages to become closed. Rather than run an UPDATE over production, the lifecycle column is nullable and NULL is answered from the row itself — a finished session is closed, a working one is open. Nothing to run, nothing to get wrong, and no finished report can come back as a live shortlist because a column was added underneath it.

Two Phase 4 items left undone

Mine

Keyset paging, and merging the builder and the results screen into one component. Both are refactors of a 1,585-line file with real regression risk and no user-visible gain today — offset paging is correct here because the list is ordered by a stored score that does not change.

Testing it yourself

About twenty minutes. Order matters — step 4 proves the thing step 6 assumes.

Local only. npm run data:test registers a company and spends capacity. Never run it against production.

  1. Get on the branch and start it

    git checkout rolling-triage
npm run build
npm run dev

    The boot log should mention the retention sweep in log-only mode. If it says it deleted anything, stop and tell me.

  2. Make a test account with sample CVs

    npm run data:test

    Prints a join key, username and password, creates a Triage with five applicants, and leaves three more CVs in sample-cvs/ for later.

  3. Sign in and open the Triage

    The session bar shows Open, an Add CVs button, and Pause and Close. The rail row shows “N of M analysed” and a date.

  4. Add the three held-back CVs

    Press Add CVs and pick them from sample-cvs/. This is the whole feature.

    They appear in the list in their place by score, not at the top, each with a New chip. Every score already on screen is unchanged — that is the thing to actually check. Your balance falls by exactly three.

  5. Check you were charged once, per delivery

    npm run triage:audit

    Two deliveries. Unpaid deliveries holding CVs: 0 and totals disagreeing with deliveries: 0. Anything else is a bug — send me the output.

  6. Mark somebody as not proceeding

    Use the ⋯ menu on a card.

    They vanish from the list, and a line appears saying one applicant is hidden, with a link to show them. They are still in the ranking — that is deliberate, so a colleague does not re-read the same CV.

  7. Close the session, then try to add more

    The bar shows Closed and a date the CVs will be deleted. Add CVs is disabled. The list still reads. Reopen puts it back and the date disappears.

  8. Delete one CV

    The route is DELETE /api/hr/triage/:id/applicants/:applicantId; there is no button for it yet.

    The row goes, the file goes, your balance does not move. Add another CV afterwards and confirm it still gets analysed — that specific sequence is what the review found broken, and it is the one worth checking by hand.

  9. Read the drafted legal wording

    Open /terms and /privacy on the dev server. Red dashed boxes. They are not on the live site and cannot be.

  10. Run the suites

    # in another terminal, with the spare server running on 5199
CKING_URL=http://localhost:5199 npm run test:triage-charge
CKING_URL=http://localhost:5199 npm run test:triage-lifecycle
CKING_URL=http://localhost:5199 npm run test:triage-drop

    “All checks passed.” on each. Node 24 crashes on exit even after a clean run, so that line is the verdict, not the exit code.

What a full test run costs

The test suites cost nothing: there is no API key on the test server, so every analysis falls back to keyword matching. The numbers below are for clicking through the product with a real key.

What CVs read At Opus / high At Sonnet / medium
The sample Triage (5 CVs) 5 ≈ $0.75 ≈ $0.06
Adding 3 more 3 ≈ $0.45 ≈ $0.04
One JD parse per delivery — ≈ $0.06 ≈ $0.01
The walkthrough above 8 ≈ $1.26 ≈ $0.11

These are estimates from prompt sizes, not measurements. The real per-CV number comes from npm run ai:cost --days 1 after a run with a key set — which is also the cost test that decides whether Add CVs goes live.

A three-CV delivery is the expensive shape: prompt caching pays for itself across a batch of fifty and barely at all across three, so small drops cost more per CV than a big pile does. Worth knowing before promising “add a few at a time”.

What the reviews found

Each phase was read adversarially by someone who did not write it. Three reviews, nineteen real defects, all fixed. The five worth knowing about:

  • Deleting the top of a ranking stranded the next delivery, permanently. Ranks were issued above the highest surviving rank, but the analysis cursor only moves forward — so the next pile was numbered underneath it and could never be selected by anything. Paid for, parsed, invisible.
  • One unreadable file refunded an entire session. On sessions predating deliveries, a single scanned photograph handed back all 36 CVs of capacity and the other 35 were analysed free.
  • A second delivery failing refunded everything and kept working. The test for “is this the first pile” asked whether anything had been ranked yet, which is false in the ordinary case.
  • The retention scan went blind past 5,000 CVs. With deletion off the window never slides, so the log the whole log-only period exists to produce was quietly partial — and --triage <id> answered “nothing is due” for any session past that point, on the exact command an erasure request needs.
  • The error handler deleted files that surviving rows pointed at. Found while building, not by a review. It undid the previous phase's fix one layer out, and the loss surfaced days later as an unreadable CV.

Four queue-failure fixes are covered by reasoning rather than by a test, and the code says so: forcing a batch to throw structurally means breaking the model call itself, and a test that has to win a race in order to fail passes for the wrong reason most of the time.

Every new setting

Setting Default What it does
TRIAGE_ADD_CVS on, except production Whether CVs may be added to a running Triage.
TRIAGE_LOW_WATER 50 Warn the administrator when capacity falls to this. 0 switches it off.
TRIAGE_MAX_OPEN_SESSIONS 25 How many Triages one organisation may have open at once.
TRIAGE_RETAIN_AFTER_CLOSE_DAYS 90 How long a closed session's CVs are kept.
TRIAGE_RETAIN_MAX_DAYS 365 How long any CV is kept, whatever the session is doing.
TRIAGE_RETENTION_DELETES off Whether the sweep may act. Off means it reports and stops.
TRIAGE_WAKE_MS 5000 How often the queue looks for work nobody started.

Going live

  1. Test it locally

    The walkthrough above. Nothing deploys until you have done this.

  2. Run the cost test with a real key

    npm run ai:cost --days 1

    Pick the effort setting from the real per-CV number, not the estimate.

  3. Merge, with Add CVs still off

    git push origin rolling-triage:main

    Render deploys main within about a minute. Everything ships except the button: the flag is off in production by default, so the schema, the charging and the lifecycle all go live while nothing changes for a recruiter.

  4. Check the migrations landed

    npm run triage:audit

    In Render → Shell. Unpaid deliveries and disagreeing totals should both read zero.

  5. Then turn the button on

    TRIAGE_ADD_CVS=1 and a restart. No deploy, and reversible in a minute.
