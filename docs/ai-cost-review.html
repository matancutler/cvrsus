What the AI costs per CV

An answer to one question: a single model call, one CV against one job description, should cost a few cents — so where does fifty cents go? The short version is that it is about fifteen cents, and roughly two thirds of that is the model writing rather than reading. Everything here is read off the code, not measured.

The short answer

One CV judged against one job description is one call to analyseMatch, from either Search or Triage. It is not several calls, and it is not the whole pool in one prompt. What makes it expensive is that the call thinks hard, writes a long report, and re-sends the same instructions and job description for every CV.

Today

~15¢

Opus 5, high effort, full written answer, nothing cached.

After phases 1–3

~8¢

Caching and a shorter answer. No change to how anything is judged.

If the eval passes

~2–5¢

Lower effort, or Sonnet 5. Only after a measured quality comparison.

Nothing here has been measured. The local database holds no telemetry rows and the local environment has no API key, so every figure on this page is derived from prompt sizes and published prices. Phase 0 replaces them with real numbers before anything is rebuilt — and if the real figure comes back at thirty cents or more, the plan stops until we know why.

Corrections to the plain-English summary

The shape of that summary is right. Two of its numbers need changing, two of its suspects turned out to be innocent, and one it listed in passing is the largest uncapped surface in the product.

Claim Verdict What to say instead
“The three fixes” (two listed) Incomplete Caching plus a shorter answer, still on Opus at high effort, lands at ~7–12¢ — not 4¢. Thinking is most of the written output and neither fix touches it. About 4¢ needs effort high → medium; about 2¢ needs Sonnet 5. Both are quality-gated, so they follow an eval.
“re-read them at a tenth of the price” Half right Reads are a tenth, but writing the cache costs 1.25×, and the entry only exists once the first response has begun. With four workers in parallel, all four first calls pay the write price unless one is deliberately sent ahead. That is the difference between “most” and “some” of the reading cost.
“can’t cost more than about 25 cents” Right 8,000 written tokens is $0.20, plus about $0.06 read — a hard ceiling near 27¢ per CV, set by max_tokens.
“asked twice when the first answer fails” Not it The SDK retries only on network, 429 and 5xx errors, none of which are billed. Triage batch retries redo only applicants that are not yet scored. A refusal is billed, but it is not retried — it falls back to the deterministic score. Worst case one wasted call, not two.
“testing” Not it The local .env has no ANTHROPIC_API_KEY and the AI suites stub fetch. Local tests cost nothing at all.
“the free demo” Bigger than it looks It runs the full Opus pipeline for anonymous visitors — twenty-five deep analyses to show six cards. See the next section.
“CVs uploaded as pictures” Real, small One vision call per image at low effort, roughly 3–5¢ a page.
“your database records the real numbers” Triage only Search records no tokens at all, and demo spend is invisible. Once caching lands, the recorded input_tokens will undercount unless the cache fields are stored alongside it.
“give the explanation the verdicts, don’t ask it to decide again” Keep this Exactly right, and it is the whole risk of that phase. One addition: most of the explanation needs no model at all — strengths and gaps are derivable from the verdicts in code, for nothing.

Two things the code says that change the picture

A launched Triage analyses fifty CVs, not twenty-five

TRIAGE_INITIAL_DEEP defaults to 50 (server/src/triage.js:46); the 25 is the rolling tranche fetched afterwards as the recruiter scrolls. So a Triage commits to roughly $6–9 the moment it is launched, before anyone has scrolled anywhere, and about $12–18 for a 100-CV pile read to the end. The “$12.50 per 100 free CVs” in the summary is about right; my earlier “first 25” framing was not.

The public demo runs the full Opus pipeline for anonymous visitors

runPublicSearch (server/src/publicDemo.js:198) calls the same runSearch a paying recruiter does: the job description is parsed, twenty-five candidates are analysed at high effort, and six are shown. Identical job descriptions share a job row — 144 demo searches have so far produced only 7 jobs — but every distinct description a stranger pastes costs about $3–5.

The only limit is eight searches per hour per browser fingerprint. There is no global ceiling, no daily allowance, and no telemetry: demo spend is the one surface of the product that cannot be seen in the database at all. If the real bill is materially above fifteen cents a CV, this is the first place to look.

Two smaller ones

Nothing is cancelled when a recruiter closes the tab. No abort signal is wired from the HTTP request into runSearch, so a page of twenty-five analyses runs to completion whether or not anyone is still waiting for it.

Changing the model re-analyses everything once. The model name is part of the analysis cache key (server/src/matching/analysis.js:24), as is VERSIONS.scoring. Phase 4 handles it by reading rows written by any model while writing new ones under the current one.

Where a CV’s money goes

Opus 5 is $5 per million tokens read and $25 per million written; the model’s private thinking is billed as writing. Token counts use the current tokenizer, about 2.5 characters per token — which makes them some 40% higher than my first estimate.

Roughly 35% reading, 65% writing. Caching addresses the 35%; a shorter answer addresses about a third of the 65%; thinking is the rest. Only the per-requirement verdicts decide the score — it is computed in code from them — so the remainder is explanation, and since the Triage card stopped showing reasoning it is prose most recruiters never open.

The plan

Four to five working days in total. Fifteen cents down to four or five is phases 0–3 plus the effort change — roughly two and a half days. Two cents needs the Sonnet eval to pass.

  1. Measure · half a day, nothing changes

    • npm run ai:cost: read triage_cost_events and ai_failures, print dollars per CV by stage and model against a price table. Run it on Render, where the real rows are.
    • Count the demo’s spend to date: distinct job_id in public_searches, times about $4.
    • One free countTokens call on a real description and CV, to pin the true prefix size.

    There is a measured cost per CV and a real read/write split. If it is thirty cents or more, stop and find out why before changing anything — it would mean something is happening that reading the code does not explain.

  2. Savings with no effect on quality · one day

    • Cache the shared prefix in analyseMatch: mark the system block, and split the user message into [description + criteria + instruction] and [this candidate]. Two of the four available breakpoints. The prefix is already in the right order, so nothing needs rearranging. Opus 5’s minimum cacheable prefix is 512 tokens and ours is about 7,000; that caching coexists with a JSON schema needs proving on the first call rather than assuming.
    • Warm the cache before fanning out: send the first candidate’s call, release the other three workers when it starts responding. No extra call, about two seconds of delay.
    • Telemetry that survives caching: record the cache-write and cache-read token counts as well as the plain ones, and extend the same telemetry to Search and the demo, which record nothing today. Without this, Phase 1 makes the recorded token count look like a saving it is not.
    • Cap the demo: analyse only the eight candidates it might show rather than twenty-five, and add a global daily allowance beyond which it falls back to deterministic scoring and says so.
    • Cancel abandoned searches: wire an abort from the closed request into runSearch.

    Cache reads are at least half of everything read on the second and subsequent CVs of a page; the demo is capped; analysis-depth-check, ai-observability-check and the Triage suites pass.

  3. Ask for a shorter answer · one day

    Keep: the per-requirement verdicts (status, quote, and a reason of at most twenty-five words), confidence, location fit, seniority alignment, and a two-sentence reasoning — the Search result card prints that line, so it has to be there.

    Remove: evidence (it repeats the quotes already in the verdicts), strengths and gaps (derivable from the verdicts by tier, in code, for nothing), and move transferable and probes to Phase 3. Trim the instructions to match, which shrinks the cached prefix as well.

    The client reads derived strengths and gaps instead; both dialogs already null-check, so stored analyses in the old shape keep rendering. Do not bump VERSIONS.scoring — scoring is unchanged, and bumping it would re-analyse every reopened search.

    Written tokens are down at least 30% and the verdict distribution on the fixture set is unchanged (score-fairness-check).

  4. Write the explanation when someone opens the candidate · half to one day

    A new endpoint returns the stored explanation if one exists, and otherwise generates it: Sonnet 5, low effort, no thinking, given the verdicts that were already decided and told to explain them rather than to judge again. That detail is the whole risk of this phase — an explanation that re-decides will eventually contradict the score on screen, and recruiters will see it. A code-side check discards any explanation that treats a requirement with no evidence as met.

    About one to two cents per candidate a recruiter actually opens, against fifteen for every candidate whether opened or not. Most of the dialog — verdicts, derived strengths and gaps — renders instantly from stored data; only the written paragraph waits.

  5. Effort and model, decided by an eval · one to two days

    The largest saving and the only part with real quality risk, so it is decided by measurement rather than by argument. npm run ai:eval runs about five job descriptions against about fifteen CVs under four configurations — Opus/high as the baseline, Opus/medium, Sonnet 5/high, Sonnet 5/medium — and reports, against the baseline: per-requirement verdict agreement (exact, and counting meets/partial as adjacent), the rank correlation of fits within each job, cost per CV, and latency. One run costs about $25–30.

    Proposed rule: adopt the cheapest configuration that agrees with the baseline on at least 90% of must-have verdicts and holds a rank correlation of 0.9 or better. Expectation, to be proved right or wrong: Opus at medium effort passes comfortably; Sonnet 5 at medium passes for Triage.

    Model and effort become environment variables per call type, so the switch is a Render setting rather than a deploy, and the analysis cache reads rows written by any model while writing new ones under the current one — otherwise the switch silently re-analyses every open search.

  6. Guardrails · half a day

    • In the Console: a monthly spend limit, and a dedicated workspace for the production key so the limit is scoped to Cursus rather than to the whole account. Ten minutes, and not something code can do.
    • In the app: a per-company daily ceiling on analyses, with the deterministic fallback and an honest notice; an AI_PAUSED switch; and ai:health naming the two spend-limit failures explicitly, so a capped account is not mistaken for a broken one. Today a hit limit degrades results quietly, which is the wrong failure for something recruiters pay for.

Deliberately not doing: the Batch API for Triage

It is half price, but the first fifty CVs are what the recruiter is waiting for and the rest are fetched by scrolling. Both are interactive. Pre-analysing the whole pile in a batch buys a discount on CVs nobody scrolls to, which is not a saving.

Open decisions

Four calls that are yours, not mine. Each changes what gets built.

  • Triage initial depth: keep 50, or drop to 25?

    With the next 25 queued immediately behind it. It only saves money when a recruiter abandons a Triage after the first screen. Recommendation: 25.

  • Put the public demo on Sonnet 5 regardless of the eval?

    It is a taster, and it is the one uncapped surface in the product. Recommendation: yes.

  • Eval material: fixtures only, or real job descriptions?

    Three to five real anonymised descriptions would make the decision rule mean something. Nothing would be taken from users’ data. Recommendation: real ones, supplied by you.

  • Sequencing: strictly in order, or eval in parallel?

    Phases 1–3 in order, or start Phase 4’s eval alongside Phase 2 so the model decision is ready when the rest lands? Recommendation: in parallel.
